# 多来源信息与推荐框架

日期：2026-09-23  
主导岗位：product-analyst  
状态：v0.1 / 产品补充框架  
上游文档：`product-requirements-framework.md`

## 1. 核心判断

本产品的核心不是人工录入路线，也不是让用户填写复杂筛选表单，而是：

> 用户输入一句自然语言诉求，系统从多来源信息中组织出可解释、可追溯的路线推荐。

人工录入是信息不足时的备用入口，不是主要供给方式。

## 2. 两类用户输入必须分开

### 2.1 出行要求

用户用一句话告诉系统：

 - 谁出行；
 - 想进行什么活动；
 - 能接受多远、多久和多大难度；
 - 希望具备哪些设施或条件；
 - 计划何时出发。

系统负责从自然语言中提取这些可能的推荐条件，不要求用户逐项填写。

### 2.2 信息贡献

用户也可以提供：

- 自己知道的路线线索；
- 现场照片、设施和路况；
- 路线错误或过期信息；
- 其他平台内容的线索或链接；
- 对路线适配性的实际体验。

这些内容用于补充和修正信息资产。

两者不能混为一个“用户输入”模块：前者驱动推荐，后者补充数据。

## 3. 信息来源分层

### S1：用户直接提供

优先接收用户的现场反馈、路线线索、照片、纠错和体验信息。

特点：

- 贴近实际出行；
- 信息新鲜度可能较高；
- 质量差异较大；
- 需要保留提交者、时间和上下文。

### S2：受控外部平台来源

通过授权接口、开放数据、用户授权导入、合作接入或平台明确允许的方式获取信息。

可能包括：

- 地图和公共出行信息；
- 天气和公共服务信息；
- 合作方或景区提供的信息；
- 用户提交的外部链接或内容线索；
- 经过审查的 Skill / Connector 获取结果。

特点：

- 覆盖面和更新能力较好；
- 依赖外部平台稳定性和使用边界；
- 必须记录来源、采集时间和获取方式。

### S3：Skill / Connector 来源

通过经过审查的 Skill 或 Connector 发现、获取和整理多个平台的信息。

定位：

- 将自然语言诉求转成来源检索任务；
- 获取公开或已授权信息；
- 统一整理不同平台结果；
- 生成待治理的候选路线。

Skill 结果必须记录来源和获取时间，不能绕过平台限制，也不能默认直接成为正式路线信息。

### S4：人工录入

由产品运营人员补齐路线、设施、候选内容和纠错结果。

定位：

- 冷启动兜底；
- 处理高价值路线；
- 处理来源冲突；
- 修正自动采集无法判断的信息。

不应成为一期主要供给方式，否则产品会退化成普通的人工路线后台。

### S5：系统推导和整理

系统对已有信息进行：

- 去重；
- 归并；
- 标准化；
- 时间更新；
- 信息冲突识别；
- 推荐所需的组合和解释。

系统推导不能伪造原始事实；推导结果应能回到来源信息。

## 4. Skill 的产品定位

Skill 不是产品本身，也不是天然拥有外部平台数据的权限。

Skill 在产品中可以承担的角色是：

1. 发现和定位信息来源；
2. 按受控规则提取公开或已授权信息；
3. 对信息进行格式整理；
4. 辅助识别重复、缺失或冲突；
5. 生成待人工确认的候选信息。

Skill 不应默认承担：

- 绕过登录、验证码或访问限制；
- 未经授权批量复制受保护内容；
- 将无法确认来源的信息直接写入正式路线资产；
- 代替产品治理和人工验收；
- 直接决定路线是否适合用户。

因此，产品表达应使用“多来源采集能力”或“受控信息获取能力”，而不是把“爬虫”或“Skill 抓取”作为产品卖点。

## 5. 推荐前的信息处理闭环

```text
用户自然语言诉求
→ 诉求理解和检索条件生成
→ 来源发现
→ 信息获取
→ 来源和时间记录
→ 内容整理与去重
→ 冲突和缺失识别
→ 可信度 / 新鲜度判断
→ 形成候选路线参考
→ 根据用户诉求生成推荐
→ 展示推荐依据和不确定性
→ 用户明确采纳
→ 转为正式路线资产
```

## 6. 产品必须保留的来源语义

在产品层面，每条影响推荐的重要信息都应能回答：

- 信息来自哪里；
- 什么时候获取或提交；
- 是用户提供、外部来源、人工录入还是系统整理；
- 是否经过核验；
- 是否可能过期；
- 是否存在冲突；
- 这条信息是否足以影响推荐。

本节不规定具体字段，只规定产品必须具备可追溯语义。

## 7. 候选参考与正式资产分离

外部平台和 Skill 获取的信息必须先进入候选参考层，不得直接成为正式路线资产。

### 候选参考

- 用于响应当前用户诉求；
- 可以展示给用户比较和判断；
- 必须附带来源、时间和不确定性；
- 未被用户采纳时不进入正式路线库；
- 可以在保留必要审计记录后过期或清理。

### 正式路线资产

- 仅由用户明确采纳的路线进入；
- 可被后续用户检索和推荐；
- 接受来源更新、用户反馈和运营治理；
- 必须保留采纳依据和原始来源关联。

用户的浏览、打开详情、收藏、停留或系统自动排序，不等于用户采纳；必须存在明确的“采纳路线”或等价确认动作。

## 8. 推荐结果的基本要求

推荐结果不能只给出路线名称，还应尽量说明：

- 为什么匹配当前用户要求；
- 使用了哪些关键信息；
- 哪些信息来自用户或外部来源；
- 哪些信息可能不完整或需要现场确认；
- 结果是否受时间、天气、路况等动态信息影响。

## 9. 主要产品闭环

### 用户侧

```text
输入一句自然语言出行要求
→ 获得候选推荐
→ 查看推荐依据
→ 明确采纳路线
→ 路线进入正式资产
→ 发现信息问题或补充现场信息
→ 提交反馈
```

### 信息侧

```text
外部平台 / Skill 获取 / 用户补充
→ 统一记录
→ 整理和治理
→ 形成候选信息
→ 用户采纳后转正式资产
→ 服务后续推荐
```

### 运营侧

```text
查看来源和采集记录
→ 处理冲突、异常和待核验内容
→ 确认可推荐信息
→ 观察信息是否过期
```

## 10. 当前产品优先级

### P0

- 一句自然语言出行要求输入；
- 诉求理解和基本检索；
- 基于多来源信息的推荐；
- 多个受控外部平台来源；
- 至少一种受控 Skill / Connector；
- 来源、时间和基本治理状态可追溯；
- 推荐结果能够解释主要匹配依据。
- 用户明确采纳后才能形成正式路线资产。

### P1

- 多来源去重和冲突识别；
- 信息新鲜度；
- 外部来源采集任务；
- Skill 辅助提取和候选生成；
- 用户贡献和外部来源的合并治理。

### P2

- 更多平台来源扩展；
- 自动化质量评分；
- 更复杂的个性化推荐；
- 自动发现新路线和新场景。

## 11. 产品边界与风险

### 10.1 合规边界

外部平台信息接入必须基于明确允许的方式，例如公开接口、合作授权、用户授权导入或其他合法来源。未经确认的批量抓取、绕过限制和直接复制受保护内容不能作为默认产品方案。

### 10.2 质量边界

外部来源不等于真实可靠。来源越多，不代表推荐越可信；必须保留来源、时间和冲突信息。

### 10.3 运营边界

如果所有信息都需要人工逐条确认，运营成本会吞噬产品价值；如果完全自动写入，错误信息会直接污染推荐。因此需要优先确定“哪些内容自动进入候选，哪些内容必须人工确认”。

## 12. 阶段结论

产品核心应从：

```text
路线资产维护 + 推荐
```

调整为：

```text
多来源信息采集与治理
→ 候选路线参考
→ 用户采纳
→ 正式路线资产
→ 用户要求驱动的推荐
```

人工录入保留，但降级为备用和治理手段。
