## 1. 文档定位

本文档是“户外推进（新）”的项目级产品需求框架，用于统一产品目标、用户角色、产品边界、一级模块和推进优先级。

本文档只回答“做什么、为谁做、解决什么问题以及做到什么范围”，暂不展开：

- API 和字段；

## 2. 产品定位

户外推荐是面向亲子家庭和户外出行用户的：

> 多来源户外信息采集、治理与可信路线推荐产品。

产品不是单纯的人工路线录入系统，也不是以社交关系为核心的内容社区。核心价值是汇聚用户提供的信息和经过授权获取的外部信息，经过记录、整理、核验和治理后，帮助用户快速判断路线是否适合当前出行。

## 3. 核心价值闭环

```text
用户输入出行要求
→ 系统从已沉淀信息中检索和推荐
→ 用户查看关键信息并判断是否出发
→ 用户补充路线、现场或需求相关信息
→ 系统通过授权来源或受控 Skill 获取外部信息
→ 信息被记录、去重、整理、核验和治理
→ 更新后的信息反哺推荐和路线展示
```

产品闭环由三部分组成：

1. **需求驱动推荐**：用户输入自己的出行要求，系统给出适配结果；
2. **多来源采集**：接收用户提供的信息，并从授权的外部平台或 Skill 获取信息；
3. **信息沉淀治理**：记录来源、时间、证据和可信度，形成可复用的信息资产；
4. **推荐持续改进**：将治理后的信息回流到推荐和路线展示。

## 4. 产品目标

### 4.1 用户目标

- 根据当前出行诉求快速找到适合的路线；
- 在出发前了解影响决策的核心信息；
- 能够比较路线并判断是否值得当前出发；
- 能够低成本反馈错误信息、补充现场信息或提交新线索。

### 4.2 平台目标

- 建立多来源、可追溯、可更新的路线和出行信息资产；
- 让用户贡献与外部采集信息经过整理和治理后再影响正式推荐；
- 逐步提升信息的可信度、新鲜度和完整度；
- 让同一条有效信息可以被多次检索、组合和复用。

### 4.3 运营目标

- 管理不同来源的信息进入、合并和更新；
- 处理用户纠错、补充和上传；
- 管理外部来源、采集任务和候选信息；
- 维护信息质量、可信度和新鲜度；
- 识别冲突、过期和待核验内容并推进闭环。

## 5. 目标用户与角色

### 5.1 小程序用户

主要包括：

- 亲子家庭；
- 周末短途户外用户；
- 轻量徒步、自然体验和休闲出行用户；
- 需要快速筛选路线的出行者。

用户核心任务是：

> 少做筛选，快速判断一条路线是否适合当前出行。

### 5.2 运营 / 管理人员

负责：

- 维护正式路线资产；
- 处理用户贡献；
- 治理候选路线；
- 维护基础配置和路线质量信息；
- 保持推荐结果和路线展示的可用性。

### 5.3 系统能力

系统需要支撑：

- 接收用户出行要求并返回推荐结果；
- 接收用户提供的路线、现场和需求相关信息；
- 通过授权接口、平台能力或受控 Skill 获取外部信息；
- 对不同来源的信息进行记录、归并、核验和更新；
- 路线详情信息展示；
- 用户反馈、纠错、补充和上传；
- 路线资产、来源信息、用户贡献和候选内容治理；
- 外部出行信息增强；
- 业务数据保存和运营支撑。

## 6. 产品形态与职责边界

### 6.1 小程序用户端

负责：

1. 出行诉求和偏好输入；
2. 路线推荐；
3. 路线详情和出发判断信息展示；
4. 用户提供路线、现场信息和反馈；
5. 用户授权导入或提交外部信息线索。

不负责：

- 后台路线资产治理；
- 用户贡献审核；
- 可信度和运营规则配置；
- 复杂社交关系和内容社区。

### 6.2 Web 管理后台

负责：

1. 工作台；
2. 路线资产；
3. 用户贡献；
4. 候选治理；
5. 信息来源和采集记录；
6. 基础设置及路线质量相关配置。

后台的核心职责是治理多来源信息和维护推荐资产，不替代小程序的用户消费路径。

### 6.3 后端及数据能力

负责支撑：

- 小程序推荐和详情信息；
- 用户反馈、纠错、补充和上传；
- 外部来源和 Skill 的信息获取结果接入；
- 信息来源、时间、证据和质量记录；
- 后台管理和治理；
- 路线资产、用户贡献、候选内容、来源和配置；
- 数据保存及外部出行信息增强。

具体技术架构不在本框架中锁定。

## 8. 核心用户路径

```text
进入小程序
→ 输入或选择出行诉求
→ 系统检索已沉淀信息并获取必要的外部信息
→ 获得路线推荐
→ 查看推荐理由和路线详情
→ 判断是否适合当前出行
→ 选择出发、继续比较或反馈问题
→ 提交纠错、补充或上传信息
```

框架层验收重点是：用户能够基于路线信息做出出发判断，而不仅是浏览路线列表。

## 9. 核心运营路径

```text
用户提交信息或授权外部来源
→ 系统记录来源和采集结果
→ 自动整理、去重和初步判断
→ 运营人员处理冲突、异常和待核验内容
→ 有效信息进入路线资产或候选治理
→ 路线信息质量提升
→ 推荐和详情展示得到改善
```

用户贡献不得未经治理直接覆盖正式路线资产。

## 10. 版本范围与推进优先级

### M0：基线收口

目标：明确产品、运行和文档基线，为后续推进建立统一入口。

### M1：可靠路线参考

当前首要主线调整为先验证可靠路线参考：

- 用户输入出行要求并获得基于信息资产的推荐；
- 一期用户只输入一句自然语言诉求，系统负责理解和拆解；
- 系统优先提供有来源依据的路线参考；
- 外部来源获取的路线先作为候选参考，只有用户明确采纳后才正式落地；
- 用户信息和受控外部来源信息能够进入系统记录；
- 信息来源和更新时间能够被保留；
- 用户能够查看来源、时间和匹配理由；
- 用户能够反馈路线错误或补充信息；
- 后台能够处理来源信息和反馈。

### M2：路线信息治理

后续重点：

- 候选来源和候选状态；
- 多来源去重和冲突处理；
- 路线可信度、新鲜度和信息完整度；
- 用户贡献、候选和正式路线之间的治理关系；
- 基础质量配置及治理结果追踪。

### M3：出行决策体验增强

在 M1 稳定后增强：

- 路线详情的决策价值；
- 出行计划；
- 地图、天气、停车、厕所、路况等辅助信息；
- 到达和返程相关建议。

### M4：扩展能力预留

候选方向包括：

- 圈子和社交；
- 用户共享路线；
- 更复杂的个性化推荐；
- 高级运营配置；
- 内容社区能力。

M4 不得在 M1、M2 未稳定前插队。

## 11. 当前范围

当前项目优先保证：

1. 推荐主路径可用；
2. 用户输入一句自然语言诉求后能够获得基于信息资产的推荐；
3. 系统能够从多个平台和受控 Skill 获取并整理路线信息；
4. 用户提供的信息能够进入系统记录；
5. 至少一种受控外部来源能够进入信息沉淀流程；
6. 推荐结果能够追溯到基础来源或治理后的信息；
7. 未经用户明确采纳的候选路线不得进入正式路线资产；
8. 路线详情能够支撑基本出发判断；
9. 用户贡献能够提交并进入后台；
10. 后台能够治理用户贡献、外部采集信息和路线资产；
11. 治理后的路线资产能够反哺用户侧；
12. 小程序、后台和后端职责边界清晰。

## 12. 当前非目标

当前不纳入产品主线：

- 圈子、社交和复杂用户关系；
- 商业化交易和会员体系；
- 高级个性化推荐平台；
- 复杂内容创作社区；
- 复杂审批和权限体系；
- 具体微服务拆分；
- 具体 API、数据库和 Agent 实现；
- 详细推荐权重和状态机。

- 以人工录入作为主要供给方式；
- 未经授权地批量复制其他平台内容；
- 只展示来源不明、时间不明或无法解释的信息。

## 13. 框架级验收口径

产品框架成立的条件：

- 产品定位和核心用户明确；
- 小程序、后台、后端三端边界明确；
- 推荐、路线治理、用户贡献回流形成闭环；
- 用户要求、信息采集、信息治理和推荐结果形成闭环；
- 信息来源、采集时间和治理状态具备可追溯性；
- 一级产品模块和版本优先级明确；
- 当前范围和非目标明确；
- 下游能够据此继续产出模块需求、架构方案和 UI 方案；
- 当前文档没有把技术实现细节误当成产品需求。

## 14. 待后续细化的问题

以下问题保留到后续产品或模块阶段处理：

1. 首个核心用户群是否以亲子家庭为主；
2. 推荐主要解决“路线是否适合”，还是同时解决“今天是否值得出发”；
3. 路线资产进入正式推荐的最低标准；
4. 用户“纠错、补充、上传、共享”的产品语义边界；
5. 哪些外部平台可以通过授权接口、用户授权导入或其他合法方式接入；
6. Skill 的职责是发现来源、提取信息还是辅助核验；
7. 用户贡献和外部采集信息进入正式路线、候选或其他治理区的规则；
8. 可信度、新鲜度和完整度如何影响展示与推荐；
9. 外部地图、天气和现场信息纳入哪个版本。

## 15. 阶段结论

当前可以锁定：

- 产品主方向；
- 核心价值闭环；
- 目标用户；
- 三端职责；
- 一级模块；
- M1—M4 的推进顺序；
- 多来源采集、记录、治理和推荐回流是产品主线；
- 当前范围与非目标。

当前不锁定：

- 技术架构；
- Java / Python / Agent 的职责拆分；
- 数据模型和 API；
- 推荐算法；
- 来源接入的具体技术实现；
- 详细页面和交互；
- 详细状态流和开发任务。

本框架完成后，建议下一步由产品分析岗位形成“一期可靠路线参考”模块需求卡；在来源策略和验收口径稳定后，再进入架构评估。
